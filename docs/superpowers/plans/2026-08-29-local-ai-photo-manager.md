# Local AI Photo Intelligence & Manager Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan phase-by-phase. **Deviation from the standard writing-plans format:** this project has a standing "basic-level testing only, scoped to business logic" preference (see Global Constraints), so tasks below are NOT structured as full TDD red/green/commit steps per the skill's default template — each phase is a scoped deliverable with a manual build/run verification gate, plus simple unit tests where the phase produces plain-Kotlin business logic (domain use cases, clustering/matching, tool/fsops validation).

**Goal:** Build a privacy-first, fully on-device Android photo management app with local face recognition, search, duplicate detection, natural-language search, and AI-assisted (user-confirmed) organization.

**Architecture:** Clean Architecture, modularized by layer/feature (`:core`, `:domain`, `:data:*`, `:feature:*`, `:ml:*`, `:llm:*`, `:tools`, `:fsops`), MVVM presentation via Compose, Hilt DI, Coroutines/Flow. The LLM never touches the filesystem or database directly — it only calls a validated `:tools` layer, and destructive operations always require explicit user confirmation before `:fsops` executes them. Full detail in [ARCHITECTURE.md](../../ARCHITECTURE.md).

**Tech Stack:** Kotlin, Jetpack Compose, Room, MediaStore, WorkManager, ML Kit (face detection), TFLite (face embeddings, image similarity — model TBD per Phase 4/7 evaluation), llama.cpp via JNI (local LLM, GGUF models — no Google-branded models), Room/SQLite brute-force vector search (upgradeable to `sqlite-vec`).

**Spec:** [docs/superpowers/specs/2026-08-29-local-ai-photo-manager-design.md](../specs/2026-08-29-local-ai-photo-manager-design.md)

> This is the canonical implementation plan, saved per the `superpowers:writing-plans` skill's `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md` convention. Keep this file — not a root-level copy — up to date as phases progress.

## Global Constraints

- No paid/mandatory cloud AI APIs (no OpenAI, Anthropic, Gemini, AWS AI, Firebase AI) — every AI feature runs fully on-device.
- App must operate with no internet connection after required models are installed (models are downloaded on first run, not bundled in the APK).
- **Basic-level testing only, scoped to business logic** — simple unit tests for plain Kotlin domain/use-case logic only (e.g. `:domain`, clustering/matching, `:tools`/`:fsops` validation); no UI/Compose/ViewModel/DI tests. Overrides the default full-coverage TDD task structure (see [CLAUDE.md](../../../CLAUDE.md)).
- Never commit to git unless explicitly asked in the current request.
- LLM never gets direct filesystem/database access — only validated `:tools` calls.
- Destructive/modifying filesystem operations always require explicit user confirmation.
- No library/model chosen without evaluating trade-offs first (see ARCHITECTURE.md decision log for LLM runtime, embedding models, etc.).
- Build incrementally: one phase must be stable (compiles, runs, manually verified) before the next starts.

### Phase 3: Face detection
**Status:** Done

**Deliverable:** On-device face detection only (ML Kit, no remote calls). Detect all faces per indexed photo; store photo ID, bounding box, detection confidence, orientation/rotation info. Background processing, non-blocking, skip unchanged images, resumable. Debug UI to open a photo and view detected bounding boxes.

**What was built:**
- New `:ml:vision` module (ML Kit Face Detection, `PERFORMANCE_MODE_ACCURATE`): `MlKitFaceDetectorImpl` implements `:domain`'s `FaceDetector` interface, decoding each photo at a bounded resolution (longest side capped at 1024px via `BitmapFactory.Options.inSampleSize`, computed from already-known stored dimensions — no extra "just measure" decode pass) and recycling the bitmap immediately after inference. ML Kit's on-device face detector does not expose a raw detection-confidence score (only per-attribute probabilities like smiling/eyes-open, which don't apply here) — `confidence` is documented and stored as a fixed `1.0f` per detected face, a known/intentional limitation rather than fabricated precision.
- `:domain` additions: `Face`/`DetectedFace` models (bounding boxes normalized `[0,1]`), `FaceDetector`/`FaceRepository`/`FaceDetectionScheduler` interfaces, `DetectFacesUseCase` (per-photo try/catch so one corrupted image never aborts the batch or crashes the worker; chunked in batches of 10 with progress committed after each chunk).
- `:data:database` additions: `FaceEntity` (FK to `photos.mediaStoreId`, `ON DELETE CASCADE`), `FaceDetectionStatusEntity` (progress, mirrors `IndexingStatusEntity`), two new `photos` columns (`facesDetectedAt`, `faceDetectionError`) — reset to null whenever a photo is re-upserted by the indexing pipeline, so a changed photo is automatically re-queued for detection. Room bumped to version 2 with an explicit `MIGRATION_1_2` (no destructive fallback). `FaceRepositoryImpl` and the `PhotoEntity`/`FaceEntity` ↔ domain mappers now live here (the `PhotoEntity.toDomain()` mapper moved from `:data:media`, since both `:data:media`'s and `:data:database`'s own repository impls need it).
- `:data:media` additions: `FaceDetectionWorker` (`@HiltWorker`, mirrors `IndexWorker`'s resumable-by-re-querying design) and `FaceDetectionSchedulerImpl` (immediate one-time + 6-hour periodic reconciliation, same `NO_NETWORK_REQUIRED`/`KEEP`-unique-work pattern as indexing, now extracted to a shared `WorkConstraints.kt`). `IndexWorker` triggers `FaceDetectionScheduler.scheduleImmediateDetection()` on successful completion, chaining the two stages per [ARCHITECTURE.md](../../ARCHITECTURE.md) §17 without literal `WorkContinuation` coupling.
- Debug UI: tapping a photo in the Photos grid opens `PhotoDetailScreen` (local Compose state swap within `feature:photos`, no new nav route) — decodes and displays the photo, overlays detected face bounding boxes via `Canvas`, shows face count, source EXIF orientation, and any detection error. - Tests: `DetectFacesUseCaseTest` (5 cases — no pending photos, faces saved on success, a corrupted image is flagged without aborting the batch, many-faces-per-photo, RUNNING→COMPLETE progress) against fakes, no Android dependencies. No UI/ViewModel/DI tests, per the project's testing preference.

### Phase 4: Face embeddings
**Status:** Done

**Deliverable:** Evaluate local face-embedding model options (accuracy, model size, inference speed, Android compatibility, CPU/GPU/NPU support, licensing, offline capability, quantization) and choose one with justification. Implement pipeline: photo → detected face → crop/align → local embedding model → normalized embedding → local storage. Embeddings never leave the device; stored efficiently; versioned by model version (regenerate-on-change support); avoid reprocessing the same face; efficient model loading; avoid holding large numbers of tensors in memory.

**Model evaluation** (full writeup in [ARCHITECTURE.md](../../ARCHITECTURE.md) §33):

| Model | Accuracy (LFW) | Size | Speed | License |
|---|---|---|---|---|
| **FaceNet 128-d (davidsandberg/facenet)** — chosen | ~99.5%+ | 23.7MB (FP16 TFLite) | Moderate | MIT (origin) → clean chain |
| MobileFaceNet | ~99.28% | ~1-5MB (quantized) | Fast (~24ms/face, Snapdragon 820 CPU, per published benchmarks) | Unclear/unlicensed for most circulating TFLite conversions |
| ArcFace (ResNet50) | ~99.83% | Large (ResNet50 backbone) | Slower, not mobile-optimized without further slimming | Varies by port |

**Chosen: FaceNet 128-d.** MobileFaceNet is smaller and faster, but web research turned up no circulating TFLite conversion with a clear, verifiable license — several widely-used community repos ship the `.tflite` with no LICENSE file at all (default: all-rights-reserved, not safe to redistribute in a product). FaceNet's weights trace back to davidsandberg/facenet (MIT), repackaged via the deepface library (MIT) into a TFLite conversion distributed under an Apache-2.0 repo — a clean, verifiable permissive chain end to end. Given the app already downloads models on first run rather than bundling them in the APK, FaceNet's larger size (23.7MB vs. MobileFaceNet's few MB) is an acceptable trade for license certainty in a project whose licensing evaluation is an explicit, required gate. ArcFace was ruled out for this phase as heavier and not mobile-optimized out of the box. 128-d (not 512-d) was chosen over `facenet_512.tflite` for the smaller embedding footprint (512 bytes/face vs 2048) with no meaningful accuracy loss for this use case.

**What was built:**
- New `:ml:embeddings` module: `FaceNetEmbeddingGenerator` (TFLite `Interpreter` wrapper — crop with 20% margin around the detected box → resize to 160×160 → `(pixel-127.5)/128` normalization → inference), `ModelFileStore` (resolves the model's app-private location), `HttpModelDownloader` (streams the model over the network **only** in response to an explicit user tap in Settings, verifies a pinned SHA-256 before the download is considered valid, downloads to a temp file first so an interrupted download is never mistaken for a complete model).
- `:domain` additions: `FaceEmbedding` (with manual `equals`/`hashCode` since Kotlin data classes compare `FloatArray` properties by reference, not content — a real correctness trap this phase specifically guarded against), `l2Normalize` (pure, unit-tested), `EmbeddingGenerator`/`FaceEmbeddingRepository`/`EmbeddingScheduler`/`EmbeddingModelDownloader` interfaces, `GenerateFaceEmbeddingsUseCase`.
- `:data:database`: `EmbeddingEntity` (faceId as primary key — one current-version embedding per face, replaced wholesale on regeneration, matching ARCHITECTURE.md §16's "has (current version)" cardinality; vector stored as raw float32 bytes, 512 bytes/face), `EmbeddingStatusEntity`, two new `faces` columns (`embeddingVersion`, `embeddingError`). Room bumped to version 3 with `MIGRATION_2_3`.
- `:data:media`: `EmbeddingWorker`, `EmbeddingSchedulerImpl` (immediate + 6h periodic, same pattern as indexing/detection). `FaceDetectionWorker` triggers `EmbeddingScheduler.scheduleImmediateEmbedding()` on success, chaining the third pipeline stage.
- Settings UI: an "AI Models" section with an explicit "Download face-embedding model" button, progress bar, and ready/failed states — the `INTERNET` permission is used *only* behind this explicit action, never implicitly, per the architecture's locked privacy principle.
- **Avoiding reprocessing:** a face's `embeddingVersion` is set (to the current model version) whether embedding generation succeeded *or* failed, so a permanently-bad crop isn't retried every run — only a model version bump re-queues it. `fetchFacesNeedingEmbedding()` is a single indexed query (`embeddingVersion IS NULL OR != current`), not a per-face check.
- **Memory:** exactly one bitmap crop/resize/tensor is alive at a time per face (no batching), each explicitly recycled; the source bitmap is bounded to a 1024px longest side before crop, same pattern as Phases 2/3.
- Tests: `FaceEmbeddingTest` (4 cases — L2 normalization math, zero-vector edge case, non-mutation, content-based equality) and `GenerateFaceEmbeddingsUseCaseTest` (5 cases — model-not-ready is a true no-op that touches no rows, empty pending, success path normalizes+versions correctly, a bad crop doesn't abort the batch, RUNNING→COMPLETE progress), all against fakes, no Android/TFLite dependencies.

### Phase 5: Automatic people discovery (clustering)
**Status:** Done

**Deliverable:** Cluster face embeddings into likely individuals. Support multiple initial clusters per person, merging people, splitting incorrectly grouped people, marking a face as incorrect, leaving unknown people unnamed, recalculating clusters, storing the clustering algorithm/model version. People screen: person/cluster, representative photos, photo count, face count, confidence/quality info. UI actions: "Name this person," "Merge with another person." No automatic name assignment.

**Clustering algorithm** (full rationale in [ARCHITECTURE.md](../../ARCHITECTURE.md) §38): a pure, unit-tested greedy nearest-centroid algorithm (`FaceClusterer` in `:domain`) — each face is compared by cosine similarity against every current cluster centroid (existing people, plus any new clusters formed earlier in the same run) and joins the closest one above a similarity threshold (untuned heuristic, `0.6`, no real face dataset available to calibrate — same documented limitation as Phase 4), otherwise seeds a brand-new cluster. This deliberately favors precision over recall, per the product requirement that one real person may end up as several separate clusters rather than risk an incorrect automatic merge — merging is a safe, supported user action; an automatic false-merge is much harder to detect and undo. Centroids are tracked as raw element-wise vector sums (not true averages) since L2-normalization is scale-invariant — this makes membership changes (add/remove a face) exact arithmetic with no re-averaging drift, which is what makes split/mark-incorrect/merge cheap and precise.

**What was built:**
- `:domain` additions: `FaceClusterer` (the algorithm above), `CentroidMath` (`addVector`/`subtractVector`/`cosineSimilarity`, pure), `planMerge`/`shouldDeletePersonAfterRemoval` (pure decision logic for merge naming and empty-cluster cleanup), `PersonRepository` interface, `ClusterFacesUseCase` (incremental — only faces not yet assigned to any person and not marked incorrect are processed each run; already-clustered faces, including anything the user has merged/split/named, are never touched by a normal pass).
- `:data:database`: `PersonEntity` (`centroidSum: ByteArray`, `memberCount`, `clusterAlgoVersion`, nullable `name`/`representativeFaceId`), `PersonFaceEntity` (`faceId` as primary key — a face belongs to at most one person at any instant, a deliberate simplification of the architecture's many-to-many ER model), `ClusteringStatusEntity`. Room bumped to version 4 with `MIGRATION_3_4`. `PersonRepositoryImpl` implements clustering application, naming, merge, split, and mark-incorrect — each mutation recomputes the affected person's centroid sum via exact vector add/subtract (see above) and cleans up (deletes) a person left with zero members.
- `:data:media`: `ClusteringWorker`, `ClusteringSchedulerImpl` (immediate + 6h periodic, same pattern as the other three pipeline stages). `EmbeddingWorker` triggers `ClusteringScheduler.scheduleImmediateClustering()` on success, completing the four-stage chain (index → detect → embed → cluster).
- People UI (`:feature:people`): a grid of person cards (representative photo, name-or-"Unnamed", photo/face counts, average match confidence) → tapping opens a detail screen with an editable name field ("Name this person"), a "Merge with another person" button (dialog listing every other person), and a grid of the person's member photos where long-press opens "Split into new person" / "Mark face as incorrect". A person's own detail screen auto-navigates back to the list if that person is merged away (its id ceases to exist) while the screen is open.

### Phase 6: Search by people
**Status:** Done

**Deliverable:** Deterministic (non-LLM) database/vector queries. Support: photos of a selected person, photos with multiple selected people, person + date filtering, person + folder/location filtering where metadata exists. Pagination/lazy loading, appropriate indexes.

**What was built:** A single parameterized `SearchDao.searchPhotos()` query (`:data:database`) implementing multi-person AND (intersection) via a `person_faces`/`faces` subquery grouped by photo with `HAVING COUNT(DISTINCT personId) = personCount`, plus the SQL optional-filter pattern (`(:param IS NULL OR ...)`) for date-range and GPS-bounding-box filtering — one query covers every filter combination rather than a combinatorial set of methods. Two new indexes (`index_photos_dateTakenMs`, `index_photos_latitude_longitude`) were added via Room migration 4→5. Jetpack Paging 3 (`room-paging`, `paging-compose`, pinned to 3.5.1 — the latest stable at implementation time) wires the query through `SearchRepository`/`SearchPhotosUseCase` (`:domain`, which gained a `domain.search` package with `PhotoSearchFilter`, `BoundingBox`, and a pure `LocationBoundingBoxCalculator` for point+radius→bbox conversion) to a new `SearchViewModel`/`SearchScreen` (`:feature:search`, replacing the Phase 1 placeholder) with a person-chip picker, a 5-year quick-filter row (year-granularity, not a custom date-range picker — an explicit, approved scope-cut; the query layer itself supports arbitrary millisecond ranges), a "near saved location" toggle, and a paged `LazyVerticalGrid` of results. Location filtering needed a saved point to compare against, so Settings gained a "Search location" section (lat/lon/radius text fields backed by three new DataStore keys in `SettingsRepository`/`DataStoreSettingsRepository`) — location filtering is bounding-box-only against the existing nullable `latitude`/`longitude` columns, since no folder/album metadata exists on `PhotoEntity` to filter by (an explicit, spec-documented scope cut, not an oversight). ### Phase 7: Duplicate and similar-photo detection
**Status:** Done

**Deliverable:** Exact duplicates (deterministic content hash) and visually similar photos (evaluate an appropriate local image embedding model) as two distinct concepts. No LLM. Duplicate groups, similarity scores, visually-similar groupings, burst-photo grouping where feasible. UI to inspect groups. Never auto-delete — deletion always requires explicit user confirmation.

**What was built:** A two-tier detection pipeline extending the existing index→detect→embed→cluster chain with a parallel branch: `HashWorker` computes SHA-256 (`ContentHasher`-style, via `PhotoHasherImpl` in `:data:media`) and a 64-bit perceptual dHash (`PerceptualHashCalculator`, `:domain`) for every photo, chained off `IndexWorker`. Two independent consumers follow: `HashGroupingWorker` (pure SQL/grouping — exact duplicates by identical content hash via `DetectDuplicatesUseCase`, and near-duplicate/burst groups via Hamming-distance union-find + a time-window check via `GroupNearDuplicatesAndBurstsUseCase`) and `SimilarityEmbeddingWorker` → `VisuallySimilarGroupingWorker` (a bundled MobileNetV3-Small TFLite model, converted from `tf.keras.applications` — Apache 2.0 — since no cleanly-licensed unauthenticated download URL existed the way FaceNet's did in Phase 4; grouped via `NearestCentroidClusterer`, a pure algorithm **extracted from Phase 5's `FaceClusterer`** so both face and photo clustering share one tested implementation, verified via the original `FaceClustererTest` suite passing unchanged against the extraction). Schema: `photos` gained `contentHash`/`perceptualHash`/`hashError`/`similarityEmbeddingVersion`/`similarityEmbeddingError` columns; four new tables (`duplicate_groups`/`duplicate_group_members`, `similar_groups`/`similar_group_members` with a `kind` discriminator for NEAR_DUPLICATE/BURST/VISUALLY_SIMILAR) plus `similarity_embeddings` (persisted, mirroring `EmbeddingEntity` for faces — not left in memory). Migration 5→6. UI: a "Find duplicates" action on `PhotosScreen` opens `DuplicatesScreen` (`:feature:photos`) with three tabs, per-group multi-select, and a "Delete selected" action using `MediaStore.createDeleteRequest()` (API 30+, the OS's own confirmation dialog) or a `RecoverableSecurityException`/legacy `WRITE_EXTERNAL_STORAGE` fallback below API 30 — never an automatic delete.

- `./gradlew :domain:test` — 81/81 tests passed (24 new: `NearestCentroidClustererTest`, `PerceptualHashCalculatorTest`, `PhotoGroupingTest`, and use-case tests for hashing/duplicate-detection/embedding/grouping against fakes), no regressions in the pre-existing 57 — including the original `FaceClustererTest` suite run unmodified against the new shared `NearestCentroidClusterer` as a regression-safety net for the extraction.

(2) `SimilarGroupMemberEntity` was keyed on `photoId` alone, but a photo can legitimately belong to groups of *different* kinds simultaneously (e.g. both NEAR_DUPLICATE and VISUALLY_SIMILAR) since `kind` lives on the group, not the membership row — the single shared key meant one kind's grouping pass silently evicted another kind's membership for the same photo. - **Progress state for the four new pipeline stages (hashing, hash-grouping, similarity-embedding, visually-similar-grouping) is in-memory only** (`MutableStateFlow`, not a durable Room status table like `IndexingStatus`/`FaceDetectionStatus`) — a deliberate scope-limiting choice given these stages complete in seconds to tens of seconds rather than the multi-minute face pipeline, but it means progress isn't observable across a process death mid-run the way the older stages' progress is. - **Deletion below API 29 relies on `WRITE_EXTERNAL_STORAGE` (`maxSdkVersion="28"`)**, exercised only via code review, not on an API 26-28 device/emulator (the test AVD is API 35) — the API 30+ `MediaStore.createDeleteRequest()` path is the one verified live, on-device.

### Phase 8: Natural-language AI search
**Status:** Done

**Deliverable:** Local/on-device LLM (llama.cpp) translates natural language into structured search intent and/or invokes controlled application tools; never directly accesses the filesystem or database. Controlled tool layer: `search_people`, `search_photos`, `search_by_date`, `search_by_location`, `find_duplicates`, `find_similar_photos`, `get_photo_metadata`, `get_storage_statistics`. Tool layer validates all parameters; LLM produces structured tool calls, not arbitrary code. Architect so the LLM engine/model is swappable later. Logging/tracing of query → interpreted intent → selected tool → parameters → tool result → final response, without logging unnecessary private photo content.

**What was built:** Per [the design spec](../specs/2026-08-31-phase8-nl-search-design.md), the plan's illustrative eight tools were consolidated to five (`search_people`/`search_by_date`/`search_by_location`/`search_photos` collapsed into one `search_photos` tool with optional `people`/`startDate`/`endDate`/`location`/`sortBy` params — reduces tool-misrouting risk for a small model) plus `find_duplicates`, `find_similar_photos`, `get_photo_metadata`, `get_storage_statistics`. Three new modules: `:tools` (plain Kotlin — `ToolRegistry`, `ToolValidator`, five `Tool` implementations, each a thin adapter over one existing/new `:domain` use case), `:llm:orchestration` (plain Kotlin — `GrammarBuilder` generates a GBNF grammar from the tool schemas, `ToolCallParser` parses the model's JSON via kotlinx.serialization, `ToolCallLoop` runs the retry-then-fallback orchestration, `LogcatTraceLogger`), and `:llm:runtime` (Android + native — vendors llama.cpp as a pinned git submodule at commit `c1d0e7a004015f23bc0233470b747b596f29b264` (tag `v0.3.0`), built via CMake/NDK, JNI bridge calling llama.cpp's grammar-constrained sampler API directly). `:domain`/`:data:database` gained small additive extensions: `PhotoSearchFilter.personIds` is now optional (empty = no person filter, needed for person-less queries like "largest photos") plus a `PhotoSortOrder` (newest/largest/smallest), `PhotoRepository.fetchById`/`fetchByIds`, and a new `StorageStatistics`/`StorageStatisticsRepository`/`GetStorageStatisticsUseCase` backed by simple `COUNT`/`SUM` queries (no schema/migration needed). Model: Llama-3.2-1B-Instruct, GGUF, Q4_K_M quantization, from `bartowski/Llama-3.2-1B-Instruct-GGUF` (Meta's Llama 3.2 Community License; the app's Settings/About should carry the required "Built with Llama" attribution — tracked as a Phase 11 privacy-page follow-up, not yet added to the UI). Settings gained a "Download search assistant model" section (byte-for-byte the same pattern as Phase 4's face-embedding downloader); Search screen gained an "Ask in plain English…" query box above the existing Phase 6 filters, sharing the same visual grid but backed by a bounded one-shot `List<Photo>` result (not Paging, since a tool answer is a fixed-size answer, not infinite scroll) rather than the paged Flow the deterministic filters use.

Fixed by wrapping the native call in `withContext(dispatchers.default)`, matching ARCHITECTURE.md §18's "dedicated background dispatcher, never the main thread" requirement — verified after the fix that the native crash/ANR moved to (and the work correctly now runs on) a `DefaultDispatcher` worker thread.
  2. **Malformed GBNF from Kotlin string interpolation**: `GrammarBuilder` originally built quoted GBNF terminals via `"${q}tool${q}:"` (splicing a `"` character *inside* an already-quote-delimited literal), which produces broken GBNF (`""tool":"` — an empty string literal followed by a bare, undefined `tool` token) instead of the correct escaped-quote terminal `"\"tool\":"`. `llama_sampler_init_grammar` silently returns `NULL` on a parse failure per its own documented contract, and the JNI bridge didn't check for that, so the null grammar sampler was added to the sampler chain and crashed with a real `SIGSEGV` (null pointer dereference) inside `llama_sampler_apply` on first use — caught via `adb pull`ing the device's tombstone and reading the native backtrace, not guessed.   3. **Native build performance**: AGP passes `CMAKE_BUILD_TYPE=Debug` for an Android debug variant, which disables optimizations (`-O0`) for llama.cpp/ggml's CPU-bound matrix-multiply-heavy inference code — measured at ~106 seconds total latency for a single short generation on the verification host. Forcing `set(CMAKE_BUILD_TYPE Release CACHE STRING "" FORCE)` in `CMakeLists.txt` (llama.cpp's own compute code is what needs optimizing, not this project's few-line JNI wrapper, so there's no real debugging trade-off) cut cold-start (model load + first generation) latency to ~50-59 seconds and warm (model already resident, 1-2 grammar-validation retries) latency to ~15-20 seconds on the same host.
  4. A missing Hilt `@Provides` for `GetPhotoMetadataUseCase` was caught at Dagger annotation-processing time (`[Dagger/MissingBinding]`), not silently — fixed by adding it to `RepositoryModule`'s companion object alongside the pre-existing `GetStorageStatisticsUseCase` provider.
  5. `HttpLlmModelDownloader`'s download URL (Hugging Face's `resolve/main/...`) 302-redirects to a separate CDN host; `HttpURLConnection.setInstanceFollowRedirects(true)` does not follow cross-host redirects (a real JDK limitation), so the downloader manually follows redirects via the `Location` header instead of relying on the built-in flag.

- **On-device latency was measured on a severely memory- and CPU-constrained verification host** (an 8GB-RAM development machine running the emulator, Gradle, and this session's tooling simultaneously; the host was observed low-memory-killing unrelated background apps during testing) — the ~15-60 second latencies above are a worst-case bound from a contended shared host, not a representative measurement of a real Android device's likely performance. A real-device benchmark (per this project's "do not claim a performance win without the numbers to back it" principle) is a documented follow-up for Phase 12.
- **No "Built with Llama" attribution is in the UI yet** — required by the Llama 3.2 Community License; tracked as a Phase 11 privacy/about-page follow-up rather than added ad hoc here.
- **No free-text geocoding for `location`** — `SearchPhotosTool` accepts a `location` parameter but doesn't act on it yet (an explicit, documented scope cut in the design spec §9); wiring it to the existing saved-location mechanism is a small follow-up, not attempted this phase to keep `:tools`' dependency set minimal.
- **`find_similar_photos`/`find_duplicates` take no query-specific parameters** — they surface the existing Phase 7 groupings wholesale; "find photos similar to this one" (a specific reference photo) isn't supported.
- **Native build is `arm64-v8a` only** (NDK 28.2.13676358, CMake 3.31.6), matching the architecture's target device set — no 32-bit or x86_64 native build was produced.
- **Persisted, UI-visible trace history is deferred to Phase 11's diagnostics screen** — this phase's tracing is logcat-only (`adb logcat -s LlmTrace:D`), an explicit design-spec decision, not an oversight.

### Phase 9: AI-assisted photo organization
**Status:** Done

**Deliverable:** Requests like "Organize my photos," "Put photos from my Goa trip into an album." AI never modifies files directly. Flow: user request → AI analysis → Organization Plan → validation → user review → user confirmation → execution. Plan operations: `MOVE`, `COPY`, `RENAME`, `CREATE_FOLDER`, `CREATE_ALBUM`, each with source, destination, reason, confidence where applicable. Review UI: approve all, reject all, approve individual operations, modify an operation. Execution layer (`:fsops`) validates: source exists, destination valid, permissions, collisions, path traversal, duplicate destinations, unsupported operations. LLM never executes arbitrary shell commands.

**What was built:** Per [the design spec](../specs/2026-09-01-phase9-ai-organization-design.md), Phase 8's tool-calling loop gained a sixth tool, `build_organization_plan(category, dateHint?, nameHint?)` — the LLM stays a thin classifier (`SCREENSHOTS`/`BY_DATE`/`TRIP`/`ARCHIVE`); which photos actually move is decided entirely by four deterministic, pure `:domain` strategy functions (`ScreenshotOrganizationStrategy`, `ByDateOrganizationStrategy`, `TripOrganizationStrategy` backed by a new GPS+time union-find `TripClusterer`, and `ArchiveOrganizationStrategy` reusing Phase 7's duplicate-group data), never by the LLM reasoning photo-by-photo. `CREATE_ALBUM` is a virtual, in-app-only Room collection (`Album`/`AlbumPhoto` tables) — zero filesystem writes; `MOVE`/`COPY`/`RENAME`/`CREATE_FOLDER` are real `MediaStore` operations. A new `:fsops` module (the only module with real filesystem write access) provides `PlanValidator` (source-exists/path-traversal/collision/unsupported-type checks, re-run immediately before every execution, not just at plan-build time) and `PlanExecutor`/`MediaStoreWriter` (mirrors Phase 7's `DuplicatesScreen` delete flow exactly: one `MediaStore.createWriteRequest()` consent dialog per MOVE/RENAME operation on API 30+, a `RecoverableSecurityException` catch below API 30 — sequenced one operation at a time via a `OrganizationReviewViewModel` state machine, never batched). `PhotoEntity`/`Photo` gained a `relativePath` column (Room migration 6→7, alongside the four new tables) so strategies can tell where a photo currently lives. A new `OrganizationReviewScreen` (`:feature:search`, reusing Phase 8's NL entry point) shows every proposed operation with source/destination/reason/confidence, supports approve-all/reject-all/per-operation toggle/destination editing/per-photo album-member deselection, and a final per-operation success/failure summary — never a blanket success claim on partial failure.

**Verification performed:**
- `./gradlew :domain:test :core:common:test :tools:test :llm:orchestration:test :fsops:test` — 158/158 tests passed (113 domain + 25 tools + 15 orchestration + 5 fsops; zero regressions in the pre-existing 118), covering all four organization strategies, `TripClusterer`'s union-find clustering (distance-only and time-only near-misses correctly don't join, a cluster below `MIN_PHOTOS` is discarded as noise), `PlanValidator`'s path-traversal/collision/missing-source/unsupported-type rejections, `BuildOrganizationPlanUseCase`/`ConfirmOrganizationPlanUseCase` against fakes, and the extended grammar/parser/tool-call loop. No tests for the actual `ContentResolver`/`MediaStore` write mechanics or the review UI, per this project's standing testing preference — verified manually on-device instead.
- `./gradlew :app:assembleDebug` — BUILD SUCCESSFUL; Room migration 6→7 applied cleanly to the existing on-device database (2,377 real photos carried over from Phase 6/7's performance testing) with no crash, confirmed via `PRAGMA user_version` returning `7` on a pulled copy of the on-device database.
- **Full pipeline verified end-to-end for real, including a real file move**: after fixing a real tool-misrouting issue (below), submitted "Organize my screenshots" through the actual Search screen against a real MediaStore photo (id 16) whose Room-indexed filename was set to `Screenshot_test.png` (a legitimate technique — the underlying MediaStore row and URI are real; only the matching metadata was set up for the test, the same way Phase 6/7 seeded synthetic test data via direct SQLite edits). The local LLM correctly produced `{"tool":"build_organization_plan","params":{"category":"SCREENSHOTS"}}`, the review screen rendered the proposed `CREATE_FOLDER`+`MOVE` operations with reason/confidence, tapping "Approve all" then "Execute" triggered the **real** `MediaStore.createWriteRequest()` system consent dialog ("Allow Local AI Photo Manager to modify this photo?"), and after tapping Allow the summary correctly read "2 succeeded, 0 failed." Verified independently via `adb shell content query` against the real MediaStore URI that the photo's `_display_name` became `Screenshot_test.png` and its `relative_path` became `Pictures/Screenshots/` — a genuine, confirmed file move, not just a UI claim.
- **A real bug was found and fixed during this verification pass**: the 1B model initially and consistently misrouted "Organize my screenshots" (and a rephrasing) to `search_photos` instead of `build_organization_plan` — a valid tool call that executed without error, so the existing retry-on-validation-failure logic couldn't catch it (there was no validation error to retry on, just a confidently wrong tool choice). Fixed by adding explicit few-shot examples for `build_organization_plan` to `ToolCallLoop`'s system prompt (one example per category, matching the plan's own four example requests) — verified after the fix that the same query, unmodified, correctly produced `build_organization_plan` on the first attempt.
- **Only the `SCREENSHOTS` category was verified live, end-to-end, with a real file move** (per the resource/time constraints noted in Phase 8's verification — this session's host is severely memory-constrained). `BY_DATE`, `TRIP`, and `ARCHIVE` share the identical `BuildOrganizationPlanUseCase` → `ConfirmOrganizationPlanUseCase` → `PlanExecutor` code path already proven live for `SCREENSHOTS`, and each category's photo-selection logic is independently covered by its own passing unit test suite (4, 4, and 4 cases respectively) — but their on-device UI/execution behavior specifically was not separately re-verified live in this session.

**Known limitations (non-blocking):**
- **`TripClusterer`'s `DISTANCE_THRESHOLD_METERS`/`TIME_GAP_MS`/`MIN_PHOTOS` and `ArchiveOrganizationStrategy.SCREENSHOT_AGE_MS` are named, documented, untuned heuristics** — no labeled ground-truth trip/archive dataset was available to calibrate against, the same honest treatment as every prior phase's thresholds.
- **Tool-selection accuracy required a real prompt fix during this phase** (see above) — while now verified working for the exact example requests in the plan, the underlying 1B model's tool-routing reliability for *novel* phrasings of organize-vs-search requests remains an open concern, consistent with Phase 8's already-documented tool-selection limitation.
- **Existing (pre-Phase-9) indexed photos have a `NULL` `relativePath`** until they're next re-indexed by the ordinary incremental-indexing pipeline (their `dateModifiedMs` hasn't changed, so a normal incremental pass doesn't re-scan them) — `ScreenshotOrganizationStrategy` and `ArchiveOrganizationStrategy` are unaffected (a `NULL` `relativePath` is correctly treated as "not yet organized"), but `ByDateOrganizationStrategy` requires a non-null `relativePath` matching the raw camera folder and so will not match any already-indexed photo until it's re-indexed. A full `relativePath` backfill (e.g. a one-time migration-triggered re-scan) is a reasonable follow-up, not implemented this phase.
- **Write consent is requested per-operation, not batched** — a plan with many `MOVE`/`RENAME` operations shows one system dialog per operation on API 30+, matching Phase 7's existing `DuplicatesScreen` precedent exactly rather than introducing a new batched-consent code path; this is a deliberate consistency choice, not an oversight, though it means a large plan's execution is more interactive than a single one-time grant would be.
- **`PlanValidator` is not called at plan-build time to show warnings in the review UI** — only the mandatory pre-execution check (inside `PlanExecutor`) is wired; the design spec's "informational, per-operation warning at build time" half is not implemented this phase.
- **`LogcatTraceLogger.logIntent` doesn't log `category`/`dateHint`/`nameHint`** — only the five pre-existing `ToolCall` fields are formatted into the trace line, so a `build_organization_plan` intent's actual parameters aren't visible in `adb logcat` (its correct end-to-end behavior was confirmed via the review screen and MediaStore checks instead, not via this log line). A one-line follow-up, not a functional gap.
- **No undo/operation history beyond per-operation success/failure** — full undo is Phase 10's job, as originally scoped.
- **No real place-name geocoding** — trip identification is GPS+time clustering only; a place name in the request (e.g. "Goa") is used only as the resulting album's label, never as a filter, per the design spec's explicit scope cut.
